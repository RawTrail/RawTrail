# HTTP API

RawTrail exposes a single HTTP API surface split across four audiences:

- **Agents** on macOS endpoints post telemetry and poll for commands. They authenticate with a per-host bearer token.
- **Browsers** (the admin UI) authenticate with a session cookie + CSRF token. Everything the UI does is reachable as a JSON API from the same endpoints.
- **Service accounts** (automation) authenticate with a short-lived bearer token from `POST /api/oauth/token` and call the same operator endpoints.
- **Operators / load balancers** hit `/livez`, `/readyz`, `/health` unauthenticated.

The machine-consumable spec is [`api/openapi.yaml`](api/openapi.yaml). The OpenAPI 3.1 file is the source of truth: this doc is the human overview.

Every running server also hosts a live browsable copy of the spec via Redoc:

- `https://<your-server>/api/docs` - rendered docs page
- `https://<your-server>/api/openapi.yaml` - raw spec

Both endpoints are unauthenticated (the spec is already public on the GitHub release page) and served from the same binary with no external network calls.

The scheme is always `https://`: the server presents HTTPS to clients and has no unguarded plaintext-HTTP mode (it serves plaintext only on the internal hop behind a TLS-terminating proxy, never directly to clients), and dev deployments use a self-signed cert generated by `task dev:certs`. Examples in this doc use `https://`.

## Base URL

```text
https://<your-server>/
```

All endpoints are rooted at `/api/` except the health probes and the UI. There is no versioning header; when v2 lands it gets a parallel `/api/v2/` tree.

## Content type

Request bodies are `application/json; charset=utf-8`, except that `POST /api/oauth/token` also accepts `application/x-www-form-urlencoded`, as OAuth clients send by default. Response bodies, when present, use the same type; several endpoints return `204 No Content` with an empty body. Compressed request bodies are not currently supported: do not set `Content-Encoding: gzip`.

## Auth models

### Host token (agents)

An agent POSTs `/api/enroll` once with the shared enroll secret and its hardware UUID. It receives an opaque `host_token`, stored in `/var/db/fleet-edr/enrolled.plist`. Every subsequent request carries:

```text
Authorization: Bearer <host_token>
```

Tokens are scoped to the host: agent A's token cannot read agent B's commands or post events with `host_id=B`. Revoking an enrollment (`POST /api/enrollments/{host_id}/revoke`) invalidates the host's tokens within a few seconds.

Endpoints that require a host token:

- `POST /api/events`
- `GET  /api/commands` (returns only the authenticated host's queue)
- `PUT  /api/commands/{id}` (only commands owned by the host)

### Session cookie + CSRF (browsers)

Operators authenticate via OIDC (`GET /api/auth/login` redirects to the configured IdP; the callback at `GET /api/auth/callback` mints the session) or, when the IdP is unreachable, the break-glass surface (`/admin/break-glass` for login, `/admin/break-glass/setup` for the first-boot redemption flow). Both paths set `edr_session` (HttpOnly, Secure, SameSite=Lax) directly; there is no password-based `POST /api/session` endpoint. The UI reads the per-session CSRF token from `GET /api/session` once the cookie is set. Subsequent unsafe requests (`POST`, `PUT`, `PATCH`, `DELETE`) carry:

```text
Cookie: edr_session=<opaque>
X-CSRF-Token: <csrf_token>
```

GET requests only need the cookie. Logout is `DELETE /api/session`.

Operator endpoints, which take the session cookie or a service-account bearer token (below):

- `GET /api/hosts`, `/api/hosts/{host_id}/tree`, `/api/hosts/{host_id}/processes/{pid}`. The tree reads a time window by default. `scope=chain&pin=<process id>` reads one process with its ancestors and descendants. `scope=session&session=<id>` reads one AI agent session, and `scope=story&root=<process id>` reads everything descended from one process launchd started; both read the whole scope with no time window, bounded by `limit`. The response's `links` name processes launchd started for an `open` or `launchctl submit` in the read, inferred from timing and target rather than lineage; a session or story read includes each such process and what it started.
- `GET /api/hosts/{host_id}/timeline`: one host's exec, network and DNS events, newest first, over `from` and `to`, narrowed by `type` and `text`, and keyset-paged by `cursor`. `scope=chain&pin=<process id>`, `scope=session&session=<id>` and `scope=story&root=<process id>` narrow it to the processes the matching tree read returns, and the response's `scope` object says whether the scope applied, how many processes it covers, how many of them carry no generation (their events cannot be selected) and whether it was truncated.
- `GET /api/hosts/{host_id}/activity`: what a process scope touched: the files it opened, renamed, truncated or deleted, the destinations it connected to and the names it resolved, as totals and as lists naming the process behind each entry. `scope=process` or `scope=subtree` with `process=<process id>` totals one process or it and its descendants; `scope=session&session=<id>` and `scope=story&root=<process id>` total an agent session or a story. Events are matched to a process by its exact generation, a coalesced connection counts as the occurrences it stands for, and each list is capped and says when it was cut. The `scope` object reports how far the scope reached, as on the timeline.
- `GET /api/agent-sessions`: AI agent sessions across the fleet, most recently active first, each with its agent, version, host, project directory, first and last seen, and the counts of its processes and alerts still retained (a session outlives the retention of its oldest rows, so an old session's counts shrink). Filtered by `host_id`, `session`, `agent` and the `from`/`to` window a session was active in, and keyset-paged by `cursor`.
  - `GET /api/hosts/{host_id}/agent-sessions/{session_id}/lineage` names the session a session was forked from (`forked_from_session_id`, Claude Code's `/fork`) and the sessions forked from it (`forked_session_ids`). A fork's copy of its parent's tool calls is listed under the parent only.
- `GET /api/alerts`, `/api/alerts/{id}`; `PUT /api/alerts/{id}`
  - `GET /api/alerts?host_id=<host>&agent_session=<id>` lists the alerts raised on one AI agent session's processes.
- `GET /api/commands/{id}`, `POST /api/commands`, `POST /api/commands/{id}/cancel`
- `GET /api/enrollments`, `POST /api/enrollments/{host_id}/revoke`
- `GET /api/audit-events`
- `GET` and `PATCH /api/settings/tracing`
- `GET /api/attack-coverage` -- ATT&CK Navigator layer JSON describing which techniques the registered rules cover.
- `GET /api/rules` -- per-rule documentation surfaced by the UI's `/ui/rules/<id>` page; same data feeds [`detection-rules.md`](detection-rules.md).

### Service-account bearer token (automation)

A service account exchanges its client id and secret for a 15-minute access token at `POST /api/oauth/token` (OAuth 2.0 client credentials), then sends `Authorization: Bearer <access_token>` on any operator endpoint, including the containment, detection-configuration and rule-content routes that [the OpenAPI spec](api/openapi.yaml) documents. No CSRF token is needed. `GET` and `DELETE /api/session` manage a browser session and do not accept it. See [service-accounts.md](service-accounts.md).

### No auth

- `GET /livez`
- `GET /readyz` (used by LBs; leaks nothing beyond version + DB status)
- `GET /health` (alias of `/readyz`)

## Rate limits

The enroll surface is rate-limited:

| Endpoint           | Knob                      | Default   |
| ------------------ | ------------------------- | --------- |
| `POST /api/enroll` | `EDR_ENROLL_RATE_PER_MIN` | 30/min/IP |

Over-limit requests return `429 Too Many Requests` with a `Retry-After` header. The break-glass surface (`/admin/break-glass`, `/admin/break-glass/setup`) carries its own per-IP, per-email, and per-setup-bucket rate limits internal to the break-glass package; the OIDC redirect path is not rate limited at the EDR boundary (the IdP owns abuse controls upstream).

Ingestion (`POST /api/events`), command polling, and UI read endpoints are not rate limited. If you proxy thousands of agents through a single IP (NAT), you may hit the enrollment rate limit.

## Errors

Error responses use the following shape consistently:

```json
{ "error": "unauthorized" }
```

Status codes follow HTTP semantics:

- `400` - malformed request body, invalid query param, wrong enum value
- `401` - missing / invalid auth (host token or session cookie)
- `403` - auth present but the caller isn't allowed (revoked enrollment, event `host_id` doesn't match token, etc.)
- `404` - row not found OR row not visible to this caller (we don't leak existence)
- `409` - conflict (e.g., enrollment already revoked)
- `429` - rate limited
- `500` - server-side error. Expect a retry to succeed.
- `503` - `/readyz` returns this when the DB is unreachable (`status: degraded`), or while the server is draining on SIGTERM before shutdown (`status: draining`), so a load balancer takes the replica out of rotation

## Generating clients

The OpenAPI 3.1 spec is usable with any modern codegen. Examples:

```sh
# TypeScript (via openapi-typescript)
npx openapi-typescript docs/api/openapi.yaml -o src/edr-api.ts

# Go (via oapi-codegen)
oapi-codegen -package edrapi docs/api/openapi.yaml > edrapi/client.gen.go

# Python (via openapi-python-client)
openapi-python-client generate --path docs/api/openapi.yaml
```

## What's not in the API (yet)

- Webhook / SIEM push. The server doesn't POST alerts outward; integrators poll `GET /api/alerts`. Outbound integrations ship in v1.1+.
- Cross-deployment routing. All endpoints operate on a single customer boundary per server instance, since each customer runs a dedicated instance.
- Bulk enrollment / import. Agents enroll one at a time on first boot.
- Query language for events. Process tree + host list is what the UI exposes today; a flexible event query API is on the roadmap.
